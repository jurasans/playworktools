Fable's proposal · not the agreed spec

Stop counting people. Start signing licenses.

The v2 document asks the server to know every user of every ball. That one choice creates almost every hard question in this module. Remove it, and licensing becomes simpler, private, fully offline and a real sales tool.

What v2 (the document) does

The server keeps a list of users per ball. Every new user needs internet. The server must recognise the same person on two tablets, so something about the person has to leave the device.

What I propose instead

The server signs a small license certificate per ball. The tablet checks the signature and enforces the limits itself, offline. The server only ever sees numbers, never people.

The four moves

1

Signed license certificate

The license is a signed file, not a number in a reply. Any tablet can verify it with no internet. It can carry more than a tier: limits, features, trial dates.

2

Count on the tablet, report only a number

The tablet counts its own users for the ball and blocks at the limit. It tells the server "37", not who. No user identity leaves the device, ever.

3

Limit tablets, not identities

The server already knows each tablet (the device id sent today). So the license says "up to N tablets per ball". That is the cross-tablet control, with no personal data.

4

Meter active users, not all-time users

"50 active users" (seen in the last 90 days) instead of "50 users ever". Old patients age out by themselves. Clinics never have to delete anyone to free a slot.

Why this is the right shape for Playwork: the app is offline-first and keeps all clinical data on the device. Two tablets never share patients today, so "the same user on a second tablet" is already a new local record. A server-side user list would be the first thing in the company that needs personal data in the cloud. Licensing does not need it.

How it works

1. The certificate

When a tablet registers a ball (it already calls /sensors/register at connect), the server answers with a signed certificate next to the tier number it returns today. Old app versions ignore the new field, so nothing breaks.

{
  "ball": "E4:5F:01:…",          // the sensor's id
  "tier": 2,                       // same integer as today
  "limits":   { "activeUsers": 50, "tablets": 3, "activeWindowDays": 90 },
  "features": { "clinicalTests": true, "csvExport": true, "twoBall": false },
  "trialUntil": null,              // or a date: every new ball can start with a Premium trial
  "issuedAt": "2026-11-11", "refreshBy": "2027-02-09",
  "sig": "…"                       // ECDSA P-256 signature made by the server
}
  • The app holds only the public key. It can check a certificate but cannot make one.
  • The certificate is cached on the tablet. With it, the ball works with no internet at all, including creating new users.
  • ECDSA P-256 is checked with the browser's built-in crypto (WebCrypto), so no new library is needed in the app. On the server the private key lives in AWS KMS and never leaves it.

2. Counting, on the tablet

  • A user is active on a ball if they played or tested with it in the last 90 days (the window comes from the certificate).
  • Creating a new user is allowed while active users < the limit. At the limit, only new users are blocked. Existing users always keep working.
  • Guest never counts.
  • Saved game and test results already carry the ball id and the date, so the count is a local query. No new data is collected. Results saved before the ball id was recorded simply do not count.

3. What the tablet tells the server

When it happens to be online, the tablet sends one small message per ball:

{ "ball": "E4:5F:01:…", "device": "<device id, sent today already>", "activeUsers": 37, "sessions30d": 212 }

Numbers only. The server adds them up per ball and per clinic. This is the company's first real view of how its balls are used.

4. Tablets per ball

The first time a tablet meets a ball it must be online once, exactly as today. The server gives it a tablet slot (Basic: for example 3) and the certificate. From then on that tablet needs no internet for that ball. A lost or replaced tablet is released from the Manage tool, or frees itself after not being seen for a set time.

5. When the certificate gets old

The app refreshes it silently whenever it is online. If a tablet stays offline past refreshBy:

  • Therapy never stops. Existing users keep playing and testing.
  • The trainer sees a gentle "connect to the internet to refresh the license" note.
  • After a long grace period, only creating new users pauses until the tablet goes online once.

This is also how a refund, a stolen ball or an ended subscription takes effect: the server stops renewing.

The rule above every rule: licensing may stop growth (new users, new tablets, premium features). It must never lock a patient out of their rehabilitation or hide their history.

The honest weak point

The cap is no longer exact across tablets. A Basic ball with 3 tablets could reach 3 × 50 active users. Three things make this acceptable:

  • The tablet limit bounds it, and the server sees every tablet's count. A ball reporting 140 active users is not a leak, it is a sales lead for Premium.
  • If an exact cap matters, set the certificate to split it: 50 across 3 tablets means the server hands each tablet a share (for example 20 / 20 / 10) and rebalances when they sync. Still no identities.
  • A clinic that works hard to cheat a user cap can also repackage the app. No scheme inside a tablet app stops that. Signed certificates stop the casual cases, which are the real ones.

What this unlocks for the whole company

Once the license is a signed list of limits and features, it stops being a gate and becomes the way Playwork sells.

Trials that sell themselves

Every new ball starts with 30 days of Premium. On day 31 it becomes what was bought. The clinic has already felt what it is missing. Needs no app release: it is a date in the certificate.

Upgrade at the moment of need

The cap screen shows "This ball has 50 of 50 active users" and a QR code to an upgrade page for that exact ball. After payment the server issues a new certificate and the tablet picks it up on its next sync.

Add-ons without new tiers

Sell the clinical test catalogue, CSV export, progress reports or the two-ball games as switches. The two-ball games are already behind a flag; the certificate can be that flag.

Subscriptions, if wanted

The refresh date makes a yearly plan possible next to the one-time purchase. Stop renewing and the ball falls back to its base tier, never to zero.

Clinic accounts

Group balls under one clinic. A bundle becomes "a clinic with N balls". Later, an optional clinic plan can pool active users across all its balls, which answers the bundle debate with a product instead of a rule.

A fleet view for support and sales

The Manage tool already lists balls. Add tablets per ball, active users and sessions per month. Support sees a dead ball before the clinic calls. Sales sees who is close to a cap and who stopped using the product.

Distributor and reseller keys

The same signing can issue licenses for a distributor's stock in bulk, with their own trial lengths, without giving them access to the server.

Real hardware identity (own firmware)

Today a ball is known by its Bluetooth address, which can be copied. A Playwork board can hold its own key and prove it is genuine, and can carry its certificate inside the ball, so a brand-new tablet works with it with no internet at all.

A cleaner privacy story to sell

"Playwork's servers hold no patient data. Not names, not ID numbers, not results." That sentence is true under this proposal and stays true as licensing grows. For clinics, hospitals and regulators it is worth more than an exact user cap.

Check before building these: the usage counts are licence metering, separate from the consent-gated analytics, so they must be described in the terms and the privacy notice. Selling upgrades from inside the app may fall under Google's and Apple's in-app purchase rules; a QR code to a web page and business invoicing are the usual way around that, but it needs a proper check. I have not verified either point.

Is it viable?

Yes, and it is less work than the document's v2, because it removes the hardest part (identifying people) instead of solving it.

What already exists

  • The register call at connect, returning the tier integer. The certificate is one more field in that reply.
  • A stable device id per tablet, already sent to the backend.
  • Game and test results stored with the ball id and date, encrypted on the device. The active-user count is a query over them.
  • The backend's second generation (the CDK stacks, with staging) where new routes can be added without touching the frozen first version or its API gateway.
  • The Manage tool for balls, ready to grow a fleet view.
  • A feature flag for the two-ball games, a ready first "feature switch".

Plan

1

Signed certificate, local limits · the core

Server signs a certificate per ball. App verifies and caches it, counts active users locally, blocks new users at the limit, limits tablets per ball. Old apps keep working on the tier integer. This alone replaces the document's v2.

2

Counts and the fleet view · the insight

Tablets report numbers when online. Manage tool shows tablets, active users and sessions per ball. Release a tablet slot from there.

3

Trials, feature switches, upgrade link · the revenue

Premium trial on new balls, features as switches, cap screen with an upgrade QR code. Needs a decision on pricing and on how payment is taken.

4

Clinic accounts and pooled plans · the scale

Group balls by clinic, optional pooled active-user plan, distributor keys.

5

Ball-held identity and certificate · with Playwork firmware

The ball proves it is genuine and carries its license. Depends on the Playwork board having firmware, which does not exist yet.

My rough estimate, not a commitment: phases 1 and 2 are weeks of work, not months, for the app and backend together. Phases 3 and 4 are mostly product and commercial decisions with modest code. Phase 5 follows the hardware.

What I do not know

  • Prices, sales volumes and how often clinics really hit 50 users. These decide the limits and whether pooled plans are worth it.
  • How many tablets a typical clinic uses per ball. This sets the tablet limit per tier.
  • Whether customers were promised "50 users" in a contract in words that "50 active users" would not satisfy.
  • The legal checks named on the Company upgrade page.

Decisions the company has to make

1. Direction

Server-side user list (the document) or signed certificate with local counting (this page).

2. The meter

Active users in a window (and how long: 60, 90 or 180 days) or users ever.

3. Tablets per ball

The number for each tier, for example 1 / 3 / unlimited.

4. How far to go

Stop after phase 2 (a better license) or continue to trials, add-ons and clinic accounts (a better business).

My recommendation: build phases 1 and 2 as License v2. They deliver everything the document wanted (license on the ball, many tablets, a user cap) with no personal data on the server and no internet needed for daily work. Decide phase 3 once the first real usage numbers arrive, because they will show where the money is.
